# B 站订阅判定：重放实验暴露的问题与整改清单

2026-11-19 用当天真实动态（订阅「嘟嘟脸恶作剧」`mid=3537117026191454`）做离线重放，
复现了线上「判定超时 → 原样转发」的过程，并对照了新参数。结论：病根是**输出预算被推理
token 吃光**，不是模型能力问题。下面是当时列出的问题与处理状态。

重放脚本与完整报告在 `E:\scratch\tmp\opencode\`（`bili-replay.mjs`、`bili-old.mjs`、
`bili-variance.mjs`、`bili-replay-report.md`），不入库。判定的 golden set 已经固化到
`test/fixtures/bili-judge/`（见 `test/bili-judge-golden.test.js`）。

## 复现数据

三档预算，同一批样本：

| 批次 | 初版（`200 + 320·n`，45s） | 修复版（`1500 + 600·n`，120s） | 现行（`2500 + 800·n`） |
| --- | --- | --- | --- |
| 10:08 维护开始（1 条，带图） | `reasoning=523/520`，输出 0 字符 → fail-open | 判出，`reasoning=1759/2100`（84%） | 3 次里 1 次仍打满（`3299/3300`，95.9s，0 字符），其余 `919` / `2783` |
| 11:11 视频投稿（1 条） | 正常判出 | 判出 | 判出，`reasoning=446/3300` |
| 15:44 维护结束 + 兑换码（2 条） | `reasoning=844/840`，输出 0 → 两条都原文转发 | 判出，`reasoning=960/2700` | 判出，`reasoning=2061/4100` |

单条判定实测推理消耗 262~3299 token，波动极大：同一批样本重放多次，推理 token 从 167 到
3299 都有。这也是为什么预算要给足、并且在 `max-tokens` 截断时还要能放宽重试。

`2500 + 800·n` 这一列**不是当初重放实验的产物**：882e5b9 在 1500/600 之上加它时只是预防性
余量，本表里 3300 / 4100 那几次是事后用现行参数补跑的。真正解决问题的提交是 3547146
（`200+320·n` → `1500+600·n`）。

补跑还暴露了一件事：最重的那条样本在 3300 下**仍会偶尔打满**（3 次里 1 次，`3299/3300`），
所以 2500/800 并不是白加的余量，只是把失败率从「必然」压到「偶发」。偶发的那次靠第 2 条的
放宽重试兜底，而放宽重试又受第 2 条末尾的 deadline 限制。

## 清单

### 1. 输出预算（已改，原判断需修正）

`extensions/bili-observer/bili/judge.js` 的 `JUDGE_MAX_TOKENS_BASE` / `PER_ITEM` 现在是
2500/800。

需要更正之前的说法：「1500 + 600 仍偏紧、单条约一半概率打满」**不成立**。1500/600 重放
3/3 全过，最重的一次是 `reasoning=1759/2100`（84%），离打满还有余量。打满只稳定出现在初版
`200 + 320·n`（520 / 840）——那才是当初 `by=fail` 的直接原因。

2500/800 最初是预防性余量，但用现行参数补跑后发现它并不是多余的：最重那条样本 3 次里仍有
1 次打满（`3299/3300`）。也就是说这个样本的推理长度分布有长尾，预算只能压低失败概率，
剩下的偶发失败得靠放宽重试兜底。

### 2. 截断后不会重试（已改）

`src/core/llm.js` 原来只在「输出完全为空」时放宽预算重试。截断场景是「输出半截 JSON」，
非空 → 不重试 → 直接 fail-open。现在 `runStream` 把 finish 的 `kind` 带出来，`max-tokens`
也触发一次放宽重试（`maxTokens` 翻三倍，上限 8000）。

补充一个当时没发现的坑：**放宽重试和判定超时抢同一份时间预算**。`askWithTimeout` 把整个
`ask`（含内部重试）包在同一个超时里，第一次很慢又截断时，第二次重试往往跑到一半就被掐掉，
于是「截断」被拖成「超时」，连已经救回来的半截都丢了。现在 `askWithTimeout` 把 `deadline`
一起传给 `askModel`，剩余时间不够再跑一轮时就直接交回半截结果，并在 trace 里标
`widenSkipped=deadline`。

### 3. 判定模型没有推理元数据（已查清，无需改配置）

`~/.dsh/profiles/web/cordis.patch.yml` 里 `magpie-responses/10/spark-x2.6` 只声明了
`input` 和 `compat`，没有 `reasoningEfforts`；网关 `/v1/models` 也报
`reasoning: false`、`reasoning_levels: []`。所以 `pickReasoningEffort` 查不到就干脆不传。

一度以为是问题所在，实测**不是**：

| 传入 reasoning | 推理 token / 输出 token | 耗时 |
| --- | --- | --- |
| 不传 | 758 / 878 | 16.5s |
| `minimal` | 706 / 827 | 18.1s |
| `low` | 749 / 874 | 14.9s |
| `medium` | 612 / 737 | 26.0s |
| `high` | 421 / 554 | 13.1s |

网关接受所有档位（响应里会回显 `effort`）。之前写过「推理 token 消耗与档位无关」，这个
说法**证据不足**：每档只有 n=1，而同一输入的重跑波动本身就有 167~1332。准确的说法是
**没有观察到稳定影响**——一档一次不足以下结论。`reasoningEfforts` 属于锦上添花，不是必需。

真正决定成败的是输出预算：不传 reasoning、只用 2500，把三条历史 `by=fail` 样本走一遍
`askModel` 真实路径，全部判出（66s / 24s / 22s，1/1、1/1、1/1）。
**结论：不改 profile，靠第 1、2 条的预算 + 放宽重试即可。**

### 4. 截断与「模型乱说」在日志里分不开（已改）

`judge.js` 的 `salvageObjects` 只能救「完整的前几个对象」。截断落在第一个对象内部时救不
回来（单条判定必然如此）。

现在两处判定调用都会带一个 `trace` 对象进 `askModel`，回填 `finishKind` / `maxTokens` /
`widened` / `widenSkipped` / `usage`，debug 日志用 `traceNote()` 压成一行，例如：

```
B 站动态判定没解析出结果，模型原始输出： （空） 结束=max-tokens 预算=3300 推理=3299/3300
B 站动态判定没解析出结果，模型原始输出： 我觉得这条挺重要的… 结束=stop 预算=3300 输出=20
```

一眼能分出「预算不够」和「模型没照格式说」。只判出一部分（`n/m`）也会留痕。

### 5. 观测缺失（已并入第 4 条）

`status` / `finish_reason` / `reasoning_tokens` 现在进 debug 日志，不再需要手工抓网关响应。
**没有**进 `usage.json`：那里的行只有 `in/out/cached/written`，加 reasoning 字段会波及面板
汇总与历史数据迁移，收益不抵成本。

### 6. `by=fail` 时仍然全文转发（待做，产品层）

fail-open 是故意的（宁可多推不可漏推），但转发的是完整原文，包含「立即下载首日可获取
130 抽」这类广告尾。可以退化成「标题 + 前两行」，或直接提示「这条没判成，自己去看」。
需要产品上拍板，暂不动。

### 7. 判定串行，多订阅号会拖长一轮（前提需修正）

单次判定实测 22~99 秒，`poll` 串行且有 `busy` 锁。

但「`tick` 每 60 秒会跳过、导致丢轮次」这个说法**不对**：跳过只是延后到下一轮重试，
`subIntervalMin` 默认 15 分钟，轮询窗口远宽于一次 poll 的耗时，不会丢动态。真正的问题是
多个号时一轮会拖到几分钟、推送延迟变长，属于体验问题而非正确性问题。扩订阅前再考虑并发
或限流。

### 8. 样本量太小（已做轻量版）

n=4 条、1 天、1 个号，不足以支撑统计结论。

已固化成 golden set：`test/fixtures/bili-judge/replay.json` 存了 3 个批次的原始动态形状 +
6 次真实模型输出（含那次一个字都没写出来的截断），`test/bili-judge-golden.test.js` 断言
`parseVerdicts` / `formatSummary` / `formatDigest` 的输出，不联网、不调模型。样本是逐字记录
的模型输出，不是重新生成的，见该目录的 `README.md`。

要继续扩样本，按 `replay.json` 的结构追加即可。

## 验证缺口（还没补上的）

- **超时 abort 只有单测**：`llm.js` 把 `signal` 透传到底层 stream（:240），但真实 DSH 适配器
  是否尊重 `params.signal` 没有端到端证据。已用假适配器验证「超时后 1 秒内返回、3 秒内没有
  后台续跑」，但这只能证明我们这一层没泄漏。
- **截断后放宽重试在真实重放里一次都没触发**：走 `askModel` 那次（99s）status 是 `completed`，
  唯一一次截断（`3299/3300`）是重放脚本直接 `fetch` 打网关，根本没经过 `askModel`。
  放宽重试目前只有单测覆盖，真实触发时能不能救回来仍然未知。
- **`chunk.usage` 是否带 reasoning token 明细**：`src` 里没有 `reasoningTokens` /
  `output_tokens_details` 的映射，`traceNote()` 只是「有就记」，取不到就只剩原始用量。

## 这类测试叫什么

- **记录-回放测试 / record & replay**：录真实输入，改完代码原样喂回去。最贴切。
- **影子运行 / shadow mode**：新旧两版并行跑同一份真实数据，只对比不发送。
- **差分测试 / differential testing**：同一输入喂两个版本比差异。
- **黄金样本回归 / golden-set regression**：固定样本做基准，防退化。
- 最后一步由人看合不合适，整体叫 **human-in-the-loop evaluation**。
